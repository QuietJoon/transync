# Persistence and Files

`transync` persists almost nothing, and every path it touches is one a user handed it. The CLI is where nearly all of that happens — input, output, map, HTML bundle, all from flags. The library has exactly **one** filesystem door of its own, opened since 2026-08-09 (DCR-0028 / ADR-0021): `DiskCache::open(<dir>)`, the durable cache backend, which the CLI reaches through `--cache-dir`. A library caller that never constructs one never touches disk. Nothing here is discovered, defaulted or guessed — transync has no XDG presence and no path it invents.

## Staged fileset commit

The CLI commits **the whole output set as a staged fileset commit** (DCR-0006;
terminology updated by external review P1-6): every output — `out.md`, the
alignment map, and the optional six-file `--html-out` bundle — is first staged
as `<name>.tmp.<pid>` and `fsync`ed; only after every stage succeeds is each
staged file `rename`d over its target (with a best-effort parent-directory
fsync, and a best-effort fsync of **every** directory level the run had to
create for those targets rather than only the deepest — R0003-0020). This
guarantees that a partial-failure run does not leave callers
reading a half-written translated `.md`, and that a failure during the
content-writing phase leaves **no** target touched.

If staging fails, the CLI deletes every temp file it created and exits
non-zero with untouched targets. Only a failure inside the final rename
pass — a few metadata operations — **can still leave a mixed set** of old and
new targets; the name "staged fileset commit" (not "atomic") is deliberate on
exactly this point. The `--html-out` directory is preflighted before the
provider is called (R0002-0029), so a foreign-file refusal costs neither a
partial output set nor a paid translation run; the same guard runs again at
publication time, which is the answer the rename acts on.

Rolling back the *directories* a failed staging created is **empty-only**
(R0002-0002). The levels are observed missing before the publication lock is
taken, so by the time a rollback runs a peer — a transync run that was blocked
on this run's lock and resumed when it was released — may have published into
them. The rollback therefore removes one empty directory at a time (plus its
own lock marker, and only while that marker is the directory's sole occupant)
and degrades to a no-op the moment it finds content it did not put there.

Sole occupancy answers "has a peer published here"; it cannot answer "is a peer
about to". The rollback runs *after* this run releases its own lock, which is
the moment a peer blocked behind it acquires that lock having written nothing
yet — so the rollback takes the lock itself, without waiting, before it unlinks
a marker, and holds it across the removal (R0003-0001). A marker somebody else
holds, or one the probe cannot decide about at all, leaves the whole level
alone: an unremoved empty directory is inert, and a directory removed out from
under the run that just claimed it is not.

### Publication locking (R0001-0034, DCR-0021)

Every directory a publication writes into is held under an **exclusive OS file
lock** — on a zero-byte `.transync-publish.lock` marker in that directory —
from the foreign-file guard through the last rename. Two runs sharing any
output directory therefore serialize instead of interleaving their rename
passes; the loser waits and says so on stderr. The mixed-set caveat above is
about crashes and I/O errors, not about a second run.

Each mode also locks the one directory the *other* mode would be holding
instead, which is what serializes an `--out-dir` replace against a files-mode
publish into that same tree (ti `40e2a5`; DCR-0021 recorded that nesting as a
known boundary). A fileset commit claims the deepest level that exists on the
way to a destination it has to create — for a destination that already exists
that is the destination itself, so an ordinary run locks exactly what it locked
before, and the claimed level is always one the run is creating into, so nothing
starts needing permission it did not need. A directory publish claims the target
and its `html/` subdirectory, which is the whole shape a published out-dir has.
The one nesting still uncovered is a run publishing *deeper* inside an
`--out-dir` target than `html/`.

The marker file is created once and **never removed while any run holds its
lock**: unlinking it there would let a later run lock a fresh inode at the same
path while a waiting run still held the old one. The single exception is the
empty-only rollback above, which removes a marker together with the directory
level it sits in — and only after taking that marker's lock itself, so the
sentence before this one stays true. It is a transync file, so neither the
`--html-out` nor the
`--out-dir` guard treats it as foreign content, and both directory listings
below may contain it. The kernel releases the lock when the holding process
exits — `SIGKILL` included — so a crashed run cannot block later ones.

That leaves one hole a lock *holder* cannot see, and the waiter closes it
itself (ti `8792b7`). Advisory locks report no waiters, so a run queued inside a
blocking lock call is invisible to a peer about to unlink the inode it is queued
on; when the queued run is finally granted that inode, its exclusion guards
nothing and the next run locks a fresh marker at the same path. So every
granted lock is **revalidated**: the `dev`+`ino` held has to be the `dev`+`ino`
the path names, and when it is not, the descriptor is dropped and the current
marker is locked instead (bounded, and a no-op on platforms with no file
identity in `std`). An `--out-dir` replace renames a locked target away by
design, so this is an ordinary path rather than an exceptional one.

Staging temps stamped with **another process's pid are preserved, never
reclaimed** (R0001-0036): they may belong to a live run, and the scan that
sees them runs before the lock is taken. The run names them on stderr; clearing
them is a manual `rm <dir>/*.tmp.*` with no transync run active. Only temps
carrying the running process's *own* pid are swept up in passing — and, for
`--out-dir`, only *staging* siblings: a `.<name>.backup.<pid>` is the
operator's previous output and no later run reclaims it (R0002-0001).

### `--out-dir` — directory-granularity staged commit (EXT-2026-07 P1-6)

`--out-dir <dir>` publishes the complete set into one directory rather than
scattering it across individual `--output` / `--map` / `--html-out` paths.
Everything is written and fsynced into a staged sibling directory
`.<name>.staging.<pid>.<token>` — the token random per run, the directory
created rather than adopted, so every sibling the publish deletes is one it
made (R0002-0001) — then renamed into place. The published directory
always contains `out.md`, `alignment.json`, `validation-report.json`, an
`html/` subdir holding the six-file bundle, and a `.transync-out-dir`
**ownership marker** (ti `66339b`, OI-0036) staged with the rest, so the tree
carries it from the instant it exists.

The marker is what the next run's replaceability guard asks about. Without it,
"is this a transync out-dir?" was answered by the file names alone — any
*subset* of the allow-list qualified, so a user directory holding only an
`out.md` was moved aside and its backup recursively removed with no `--force`
(OI-0036). A target holding no output at all is never asked the question —
`mkdir out && transync translate --out-dir out` is an ordinary way to start, and
a guard that exists to stop content being destroyed has nothing to say about a
directory with no content in it. It is deliberately a second marker rather than
the publication lock:
`.transync-publish.lock` is created in directories transync does **not** own,
including one a guard is about to refuse, and a lock is a claim for the duration
of a run while ownership has to outlive it. A target carrying no marker is still
replaceable when the **complete** set above is present — the shape only this
publish produces — which keeps a pre-marker bundle, or one copied by a glob that
dropped the dot-files, republishing without a flag it never needed. Both marker
names count only on a **regular file**: they are the two entries the guards skip
without looking inside, so a directory wearing one would carry nested user data
past the check that refuses a directory named `out.md`, and into the backup
`remove_dir_all`.

Onto a **fresh** target that is one atomic rename. Replacing an **existing**
target is **crash-safe, not atomic** (R0001-0035): `rename` cannot replace a
non-empty directory in place, so the old tree moves to
`.<name>.backup.<pid>.<token>` first (restored on a failed swap). A crash
between the two renames can leave a backup sibling behind, never a
half-written target — and a reader that looks between them finds *no* target. Other transync runs cannot
land in that window (publication lock); unrelated readers can. See
contracts.md §6 for the exact rules (foreign-target `--force` guard; mutual
exclusion with `--output` / `--map` / `--html-out`).

## Output directory layout (when `--html-out` is given)

```
<--html-out>/
├── index.html        # demo shell — loads sync.js, mounts source/target
├── source.html       # annotated source HTML (just the rendered blocks)
├── target.html       # annotated target HTML
├── alignment.json    # copy of --map output, served alongside the bundle
├── sync.js           # vanilla ESM sync engine
├── purify.min.js     # vendored DOMPurify (fail-closed sanitization, OI-0001 [archived])
└── .transync-publish.lock   # zero-byte publication lock marker; left behind by design
```

`transync serve --rendered <dir>` serves that directory over HTTP on `127.0.0.1:7470` (ticket `b791d6`, 2026-08-09; it was **deferred** until then and exited non-zero). It reads the directory and writes nothing: no upload path, no directory listing, no file the process creates. A request is answered only from a regular file whose canonical path is still inside the served root, so a symlink pointing out of the bundle is refused rather than followed — the one **read**-side path guard in the system, and the counterpart to the write-side guards below. Any other static HTTP server against the directory still works; the JS sync engine works against any origin that serves the six files.

## Cache directory contents (`--cache-dir` / `DiskCache::open`)

```
<cache dir>/
├── transync-cache.jsonl                       # the log — the only file ever read
├── transync-cache.jsonl.unreadable-<ts>       # a log this build could not read, rotated aside and preserved
└── transync-cache.jsonl.compact-<pid>-<nanos> # a compaction interrupted by a crash
```

Only the first is live. The other two are residue, and each has a different reason for existing:

- **`.unreadable-<ts>`** — a missing or unknown-format header rotates the log aside instead of deleting it, so the operator keeps every byte (contracts.md §1). Nothing removes these; an operator decides when they stop being interesting.
- **`.compact-<pid>-<nanos>`** — compaction rewrites the log through a temp file and one `rename`, so a crash leaves either log complete and never a hybrid. Every *failure* path removes the temp; a **crash** cannot, because nothing runs in a killed process. `DiskCache::open` therefore sweeps: a leftover under the **running process's own pid** is deleted unless a compaction running right now holds that name, and one under **any other pid** is left alone and named in a warning, because a foreign pid is not evidence of death (ADR-0024, the same rule the publication temps follow). **Expect the second branch after a real crash**: the restarted run has a new pid, so the sweep reports the file rather than removing it, and it stays until somebody deletes it. Leftovers are inert — never replayed, never counted against the byte budget — and an operator may delete `transync-cache.jsonl.compact-*` whenever no run is active. (ti `d51ed7`.)

Concurrent runs sharing one cache directory are unsupported (contracts.md §1); this is the one place where that shows up as a file an operator may have to remove by hand.

## Path safety

- The CLI rejects `--html-out` paths that already contain non-`transync` files unless `--force` is given. This prevents a stray `transync translate --html-out /Users/me` from clobbering a home directory.
- Symlink/canonicalization rejection is **not** implemented yet — the CLI does not resolve `--output` / `--map` / `--html-out` against a base directory. If you point them at a symlinked path the underlying file gets written. Treat this as a soft contract until the canonicalization guard lands. Canonicalization *is* used for one narrower question: deciding whether two destinations in one run name the same file (R0002-0032). `out.md`, `./out.md`, `a/../out.md` and a path through a symlinked parent are one destination and the run refuses up front; a destination that is *itself* a symlink is not the same destination as its target, because publication renames over the link entry rather than through it.
- Under `--out-dir`, every staged entry must be a non-empty relative path of ordinary components (R0002-0004) — an absolute or `..`-bearing entry is refused before anything is opened, so the published tree can never be assembled from writes outside it.
- **`--cache-dir` is exempt from every guard above**, and that is a decision rather than a gap. `DiskCache::open` calls `create_dir_all` on the path it was handed and starts writing: no foreign-file preflight, no `--force`, no publication lock, and no place in the same-destination canonicalization check the output paths get (that set is `--output`, `--map`, `--validation-report` and the `--html-out` bundle — the cache is not in it, so a cache directory that happens to sit under an output path is not a collision the run refuses). What makes the exemption safe is the file set rather than a check: the backend reads exactly one name, `transync-cache.jsonl`, and creates only that name and the two sibling shapes listed above, so pointing `--cache-dir` at a directory of unrelated files leaves a log beside them and touches nothing else — there is no counterpart here to the home-directory clobber `--html-out`'s guard exists to stop. The one pre-existing file it ever moves is a file literally named `transync-cache.jsonl` that this build cannot read as a format-1 log, and that one is **rotated aside to `.unreadable-<ts>`, never deleted** (contracts.md §1). A directory it cannot use at all is not a refusal either: the CLI warns once and the run continues on a fresh in-memory cache (contracts.md §6), because at that boundary a cache is an accelerator and an unwritable path must not kill a translation the user asked for.
- Profile TOML paths are read-only — the CLI never writes back to `--profile`.

## What `transync` does **not** persist

- Translation cache — **by default**. `InMemoryCache` is process-lifetime and persists nothing, which is what a run with no `--cache-dir` gets. It stops being true the moment a caller asks for durability: `transync translate --cache-dir <dir>` opens a `DiskCache` over `<dir>/transync-cache.jsonl`, a versioned JSON-lines log replayed at open (DCR-0028 / ADR-0021, 2026-08-09). That directory is the caller's path — the library never picks or discovers one — which is why the cache is listed here as something transync does not persist *on its own* rather than as something it cannot persist. The old "in-memory only, per ADR-0002 reasoning mirrored from resp-translator" line was true until that day; the deferral's premise, that results are not durably valuable, does not hold for paid-for provider output over a whole document.
- Validation reports are in-memory (`ValidationReport` returned to the caller) unless the user opts in: `--validation-report <path>` writes the per-unit report as JSON (OI-0012 [archived]).
- Per-batch retry history.
- API keys — `OPENAI_API_KEY` is read from the environment by `transync-openai`, and `ANTHROPIC_API_KEY` by `transync-anthropic` since DCR-0029; one variable per provider crate, and neither is ever written.
- Anything in `~/.config` or `~/.cache`. The library and CLI have no XDG presence in MVP.

## Fixture inputs

`crates/transync/tests/fixtures/` holds the sample documents driving the integration tests. They are repository-tracked test inputs, not "persistent state" in the user-facing sense.

**The directory itself is the authority on the set** — read it rather than a listing here, so a fixture landing does not make this section wrong. What is stable is the convention it follows:

- One `scn-NN-<slug>.md` per scenario needing a document of its own, numbered after the `scenario-matrix.md` row it serves. A scenario may own more than one file — SCN-04 carries the fenced and the indented spelling of a code block separately — and a scenario exercised inside another scenario's document owns none.
- `scn-14-full.md` is the everything-document, and also the input the SCN-12 CLI run drives. `scn-15-html-blocks.md` carries the raw-HTML shapes (ADR-0018 / DCR-0016).
- A fixture that serves no numbered scenario is named for what it exercises instead (`reader-honesty.md`).
- `scn-07-validation-retry.md` and `scn-08-fallback.md` are only meaningful driven by `MockTranslator` — they exist to make a validator reject and a unit fall back.
- SCN-13 is browser-side and has no fixture of its own: its input is the SCN-12 output.
