# 배치가 섹션 경계에서 멈추는 이유

번역 실행은 문서의 블록을 한 번에 하나씩 전송하지 않습니다. 블록은 배치로 패킹되며, 각 배치는 하나의 요청이 됩니다. 패킹이 작동하는 방식은 주로 예산의 문제입니다 — 추정된 입력이나 추정된 응답이 초과할 때까지 유닛을 계속 추가한 다음 새 배치를 시작합니다 — 그러나 예산을 완전히 재정의하는 한 가지 규칙이 있습니다:

**배치의 유닛은 항상 하나의 섹션에서 옵니다.** 유닛 리스트는 아무것도 패킹되기 전에 모든 제목에서 파티셔닝되며, 각 섹션은 자체적으로 패킹됩니다. 어떤 요청도 두 개의 서로 다른 제목에서 온 블록을 포함하지 않습니다.

여기서 섹션은 원문에서 보이는 그대로입니다: `#`에서 `######`까지 임의 레벨의 제목이 하나의 섹션을 시작하며, 제목은 자신이 *닫는* 섹션이 아니라 자신이 *여는* 섹션에 속합니다. 문서의 첫 번째 제목 앞의 모든 내용은 자체 섹션인 서문(preamble)입니다. 제목이 전혀 없는 문서는 하나의 섹션이며, 이것이 플랫한 문서가 항상 그랬던 것처럼 정확하게 패킹되는 이유입니다.

## 이 규칙이 제공하는 이점

### 의미를 가질 수 있는 용어집 범위

이것이 규칙이 존재하는 이유입니다. `scope = "section"`은 아무것도 수행하기 전 오랫동안 프로필 스키마에 존재했으며, 장애물은 매칭 로직이 아니었습니다 — 배치가 한 섹션의 꼬리와 다음 섹션의 머리를 포함할 수 있어서 "어떤 용어집 항목이 이 요청의 시스템 프롬프트에 적용되는가"에 대한 단일 답이 없었다는 점이었습니다. 사용 가능한 모든 답이 틀렸습니다: 범위 지정된 항목을 렌더링하면 섹션 외부의 블록을 조종하고, 이를 드롭하면 내부의 블록을 조종하지 못합니다.

배치를 하나의 섹션으로 격리하면 질문에 답할 수 있게 되며, 그 답이 각 요청의 프롬프트가 컴파일되는 기반이 됩니다. 해소 규칙 자체에 대해서는 [용어집 항목이 해소되는 방법](./how-glossary-entries-are-resolved.md)을 참조하십시오.

### 한 가지 주제에 관한 컨텍스트

배치의 모든 유닛은 이제 동일한 제목 아래에 위치합니다. 모델이 단락을 번역하는 동안 읽는 주변 자료는 요청의 첫 번째 절반이 릴리스 노트이고 두 번째 절반이 API 테이블인 경계를 넘나드는 혼합물이 아니라 문서의 동일한 부분에서 온 자료입니다. 이것은 용어집 이점보다 소프트한 이점입니다 — 여기서는 아무것도 측정하지 않는 번역 품질에 대한 주장입니다 — 그러나 이것은 자연스러운 결과이며 동일한 방향을 가리킵니다.

### 올바른 프롬프트로부터 가격이 매겨진 요청당 예약

모든 요청의 일부는 고정 오버헤드입니다: 컴파일된 시스템 프롬프트, 조립된 지시문 엔벨로프, 두 개의 언어 레이블. 유닛이 패킹되기 전에 해당 오버헤드가 측정되어 입력 예산에서 차감되므로 패킹이 초과될 수 없습니다. 배치가 하나의 섹션에 속하기 때문에, 해당 차감은 문서 전체의 최악 케이스보다는 *섹션 자체의* 컴파일된 프롬프트를 사용할 수 있으므로 예약이 더 보수적이 아닌 더 정밀해집니다. 동일한 속성이 재시도에도 이어집니다: 재시도는 배치 내에서 재패킹하며 배치는 단일 섹션이므로 예산은 마지막 라운드에서와 첫 번째 라운드에서 동일합니다.

## 이 규칙이 치르는 비용

이 프로젝트가 가장 자주 지적받는 바로 그 문서들에 비용이 가장 크게 미치기 때문에, 이에 대해 솔직해질 가치가 있습니다.

**제목이 풍부한 문서는 예산을 어떻게 설정하든 섹션당 최소 하나의 배치를 디스패치합니다.** 참조 페이지, API 문서, FAQ, 변경 이력 — 많은 제목 아래에 대부분 짧은 섹션이 있는 모든 문서 — 은 원시 토큰 산술이 시사하는 것보다 훨씬 더 많은 요청을 생성할 것입니다. `[batching].target_input_tokens_per_batch` 또는 `max_units_per_batch`를 늘려도 이것은 변경되지 않습니다: 해당 예산은 섹션 *내부*에서 묶이며, 패커의 어떤 것도 두 섹션을 병합하지 않습니다. 자체 `###` 아래의 10줄짜리 섹션은 예산이 전체 문서를 삼킬 수 있었더라도 하나의 요청입니다.

**작은 후속 섹션들은 병합되지 않습니다.** "아주 작다면 이웃에 붙이자"라는 완화책은 없습니다. 하나의 제목과 두 문장으로 이루어진 섹션은 역시 하나의 제목과 두 문장으로 이루어진 형제 섹션 옆에서 자체 요청을 받습니다.

**더 많은 요청은 더 많은 지연 시간과 더 많은 요청당 오버헤드를 의미합니다.** 시스템 프롬프트는 항상 배치당 한 번 지불되었습니다; 증가하는 것은 배치 수이므로 고정 오버헤드가 더 여러 번 지불되고 실행은 왕복에 더 많은 벽시계 시간을 소비합니다. *유닛의* 비용에 대한 어떤 것도 변경되지 않습니다 — 어떤 방식이든 동일한 블록이 번역됩니다 — 그러나 이를 둘러싼 엔벨로프는 요청당 지불됩니다.

캐시 결과도 존재하며 양방향으로 작용합니다. 요청의 프롬프트가 이제 섹션별로 컴파일되므로 동일한 용어집으로 해소되는 두 섹션은 동일한 프롬프트 바이트로 컴파일되고 그 유닛들은 캐시 항목을 공유할 수 있습니다. 자신의 섹션이 해소된 용어집에서만 차이가 나는 두 유닛은 공유를 중단합니다 — 모델이 실제로 그들에 대해 다른 프롬프트를 읽었으므로 올바릅니다. 섹션 범위 항목이 없는 프로필은 전체 실행에 대해 정확히 하나의 그러한 컴파일을 가지므로 그 프롬프트와 캐시 키는 섹션 일관성이 존재하기 전과 바이트 단위로 동일합니다; 메커니즘은 프로필이 범위를 사용할 때까지 보이지 않습니다.

## 반대 방향으로 실행되는 한 가지 예외

하나의 요청에 맞지 않는 섹션은 여전히 여러 요청에 걸쳐 분할됩니다. 섹션 내부에서 예산이 부족해지면 패킹은 항상 했던 작업을 수행합니다 — 배치를 채우고 다른 배치를 시작합니다 — 그리고 결과적인 모든 배치는 해당 섹션 내부에 유지됩니다. 이것이 한 섹션의 유닛을 분리하는 유일한 요소입니다.

규칙의 전체 형상인 비대칭성에 유의하십시오: 섹션은 여러 배치에 걸쳐 *분할될 수 있지만*, 두 섹션이 하나로 *병합되지는 않습니다*. 배치 번호 부여는 어떤 방식이든 영향받지 않습니다 — 섹션들이 어떻게 나누었든 상관없이 전체 문서에 걸쳐 1에서 N까지 단일 문서 순서 시퀀스로 유지됩니다.

## 작은 섹션들이 병합되지 않는 이유 — 및 제공되지 않는 사항

명백한 완화책이 설계 시점에 고려되고 명시되었습니다: **인접한 전체 섹션들의 유효 용어집이 동일할 때 배치를 공유하도록 허용하는 것**. 해당 버전은 용어집 정확성을 보존하고(병합 처리된 섹션은 단독으로 읽었을 동일한 프롬프트를 읽음) 섹션의 유닛을 결코 분리하지 않으며, 섹션 범위가 없는 용어집의 경우 모든 섹션이 동일한 용어집으로 해소되므로 이전의 요청 수를 거의 정확하게 복원할 것입니다. 그러나 작성된 규칙에는 실패합니다 — 그러한 배치는 섹션 경계를 포함합니다 — 따라서 함께 따라가기보다는 자체적인 결정이 필요했습니다.

해당 결정이 내려졌으며 답은 **2027년으로 연기되었습니다**. 거부되지 않음: 프로젝트의 백로그에 `section-batch-coalescing` 항목 아래 재방문 날짜가 지정되어 추적됨. 조건보다는 날짜를 지정한 이유가 거기에 기록되어 있으며 복기할 가치가 있습니다. 알려지지 않은 내용에 대해 정직하기 때문입니다: 자연스러운 조건 — "실제 요청 수 통증이 관찰되면 재방문" — 은 대량으로 제목이 풍부한 문서를 실행하는 누군가를 필요로 하며, 아직 그러한 측정이 존재하지 않습니다. 날짜는 질문이 다시 던져짐을 보장합니다; 조건이 먼저 발생하면 일찍 물어볼 이유가 됩니다.

단순한 문자 그대로의 해석이 아닌 이유로 엄격한 격리가 먼저 출하되었습니다. 위임된 수락 기준이 말하는 바이며 위의 비대칭성이 이유입니다: 승인된 예외는 섹션을 여러 배치에 걸쳐 분할하며 결코 두 섹션을 하나로 병합하지 않습니다. 그 이상으로 병합은 나중에 추가하기 저렴하며 기본값이 이에 의존하게 되면 조용히 제거하기 불가능합니다 — 따라서 엄격한 버전을 먼저 출하하면 양방향 모두 옵션이 열려 있습니다.

**오늘날 이 중 아무것도 존재하지 않으며 프로필에 작성되어서는 안 됩니다.** 이것이 작성되는 경우 스케치된 형상은 기본적으로 끄기로 설정된 옵트인 `[batching].coalesce_sections` 노브입니다. 그러한 키, CLI 플래그, 그 뒤의 코드는 전혀 존재하지 않습니다. `[batching]` 테이블에 `coalesce_sections`를 넣으면 stderr에 `unknown profile key` 경고가 발생하며 실행에 대한 아무것도 변경하지 않습니다.
