# 스크롤 백분율이 아닌 블록 (Block) ID 동기화 (Sync)인 이유

transync는 원문 (Source) 문서와 번역문을 나란히 렌더링하고 두 패널이 함께 스크롤되도록 유지합니다. 이를 구현하는 가장 직관적으로 보이는 방법 — 문서 높이의 백분율로 스크롤 위치를 맞추는 것 — 은 이 프로젝트가 의도적으로 구축하지 않은 방식이며, 그 이유는 이후 따르는 레이어를 다루기 전에 이해할 가치가 있습니다.

## 직관적인 접근 방식의 문제점

스크롤 백분율 동기화 (Sync)는 두 문서의 형상이 같다고 가정합니다: 원문 (Source)의 40% 지점이 번역문의 40% 지점과 "동일한 위치"라는 것입니다. 하지만 실제로 그런 경우는 드뭅니다. 번역된 단락은 거의 매번 원문 (Source)보다 길거나 짧습니다 (한국어와 일본어는 통상 원문 (Source) 토큰 수의 1.3–1.8배에 달함). 테이블은 행 수는 유지되지만 셀 너비가 다르고, 제목은 한 언어에서는 두 줄로, 다른 언어에서는 한 줄로 줄바꿈될 수 있습니다. 백분율 동기화 (Sync)는 은밀하게 성능이 저하됩니다 — 오류 없이 문서가 길어질수록 두 패널 간의 이탈이 심해져, 독자가 두 패널에서 서로 관련 없는 콘텐츠를 보게 만듭니다.

이탈을 해결하지만 다른 실패와 맞바꾸는 대안은 서수 인덱스에 의한 문장 수준 페어링 방식입니다 (이 프로젝트의 참조 구현체 중 하나인 `LLM-API/LLM-Trans`가 취하는 방식): 두 문서를 모두 문장으로 세그먼트화하고 원문 (Source)의 문장 *N*을 번역문의 문장 *N*과 페어링합니다. 이 방식은 모델이 두 개의 원문 (Source) 문장을 하나로 병합하거나, 하나를 둘로 나누거나, 문장 경계를 넘어 절의 순서를 바꿀 때까지는 정상 동작하지만 — 이들은 예외 케이스가 아닌 일반적인 번역 동작임 — 그 시점 이후의 모든 페어링은 은밀하게 잘못되게 됩니다.

## 결정: 한번 할당되고 결코 재도출되지 않는 단일 ID

transync의 해법(ADR-0001)은 동기화 (Sync) 관련 모든 블록 (Block)(제목, 단락, 테이블, 코드 블록 (Block), 리스트 항목, 블록 (Block)인용구)에 *원문 (Source)* 문서로부터 Rust (Rust) 파서가 한번 할당한 하나의 안정적인 ID를 부여하고, 그 동일한 ID를 이후의 모든 레이어(LLM 요청, LLM 응답, 재생성된 번역 Markdown, 정렬 (Alignment) 맵, 양쪽 패널이 마운트하는 렌더링된 HTML의 `data-sync-id` 속성)로 전달하는 것입니다. 브라우저의 동기화 (Sync) 엔진은 절대 콘텐츠로부터 위치를 계산하지 않습니다 — 한쪽 패널의 활성 블록 (Block) ID를 조회하고 DOM에 다른 쪽 패널에서 동일한 ID를 가진 요소를 요청합니다. 동기화 (Sync) 경로 어디에도 백분율은 없으며, 무엇이 무엇에 "대응하는지"에 대한 독립적인 판단도 없습니다. 대응 관계는 번역 자체를 제약하게 될 동일한 프로세스에 의해 상류에서 한번 결정되었습니다.

이것이 문장 수준이 아닌 블록 (Block) 수준인 이유이기도 합니다: 블록 (Block)은 파서가 이미 생성하고 LLM 계약이 이미 하나의 번역 요청으로 취급하는 구조적 유닛이므로, 이를 동기화 (Sync) 유닛으로 선택하더라도 Rust (Rust)와 JavaScript가 독립적으로 합의해야 하는 새로운 세그먼트화 로직이 추가되지 않습니다. 따라서 LLM-Trans 참조 구현체가 가진 실제 기능인 문장 수준의 클릭 페어링(click-to-pair)은 범위에서 제외됩니다. 프로젝트는 기본값으로 이를 지향하는 대신 이러한 트레이드오프를 명시적으로 수용했습니다.

## 이 방식이 가져다주는 이점과 비용

ID 우선 디자인 (Design)은 브라우저뿐만 아니라 더 많은 부분에서 이점을 줍니다: 이는 [계층화된 검증과 제한된 재시도/폴백 모델인 이유](./validation-retry-fallback-model.md)에 설명된 검증 (Validation) 계약의 형태도 설정합니다. LLM은 요청당 하나의 블록 (Block)을 전달받고 번역할 ID를 지정받으므로, 검증기(validator)는 콘텐츠를 보기 전에 가장 먼저 저렴하고 순수 구조적인 게이트로서 "반환된 ID 세트가 전송된 ID 세트와 일치하는가"를 검사할 수 있습니다 — 이는 관습 외에는 응답의 7번째 문장이 요청의 7번째 문장이라고 말해주는 것이 없는 문장 서수 체계에는 대응물이 없는 검사입니다. 동일한 게이트는 *귀속(attribution)* 규칙으로서의 역할도 겸합니다: 누락되거나 중복된 행은 유닛의 콘텐츠가 아닌 제공자의 엔벌로프에 대한 진술이므로, 자체 예산에 차감되고 동일한 배치의 무고한 유닛들은 손상되지 않은 채 계속 진행됩니다.

연기된 클릭 페어링 기능을 제외한 명시적 비용: 블록 (Block) 내 동기화 (Sync)가 매우 긴 블록 (Block)(200행 테이블, 긴 코드 펜스)의 경우 이상적인 수준보다 거칠다는 점입니다 — 전체 블록 (Block)이 하나의 동기화 (Sync) 앵커이므로 블록 (Block) 내부를 스크롤하더라도 블록 (Block) 경계를 넘기 전까지는 파트너 패널이 이동하지 않습니다. 프로젝트의 자체 문서에서도 이를 해결된 문제가 아니라 알려지고 수용된 거친 부분(rough edge)으로 기록하고 있습니다.

## 테이블이 모델을 위해 분할될 수는 있지만, 독자를 위해 분할되는 일은 결코 없습니다

그 200행 테이블은 디자인 (Design)에서 가장 오해하기 쉬운 규칙이 존재하는 곳이기도 하며, 이 규칙은 취지를 바꾸지 않은 채 2026-08에 형태를 변경했습니다.

테이블은 예전에 엄격하게 하나의 전체 블록 (Block)으로 번역되었습니다. 하지만 이제는 다릅니다: 출하된 기본 전략 하에서, 예상 응답이 실행의 출력 상한을 초과하는 테이블은 패킹 시점에 *행 윈도우(row window)*로 분할되어 각 윈도우가 독립된 유닛으로 디스패치, 검증 (Validation), 재시도 및 캐시됩니다 (DCR-0026). 흥미로운 질문은 테이블이 분할될 수 있는지 여부가 아니라 — 분할될 수 있음 — 왜 테이블이 여전히 셀 단위로 번역되지 않는가 하는 점이며, 이 두 가지는 혼동하기 쉽습니다.

윈도우는 **완전한 GFM 테이블**입니다: 원문 (Source) 헤더 행, 열별 정렬 (Alignment)을 전달하는 구분자 행, 그리고 원문 (Source) 순서의 본문 행 연속입니다. 고립된 셀도 아니며, 헤더가 없는 조각도 아닙니다. 이것이 윈도우를 번역 가능하게 만드는 이유입니다 — 모델은 열 헤더를 컨텍스트로 가진 테이블을 보게 되며, 종류별 검증기(validator)는 모델에 보여주지 않은 컨텍스트에서만 의미가 있는 조각이 아닌 실제 테이블을 대상으로 열 개수와 형상을 검사할 수 있습니다. 셀 단위 번역은 바로 그러한 컨텍스트를 삭제하게 됩니다: 단독 셀에는 "state"가 미국의 주인지 프로그램 상태인지 모델에 알려주는 헤더가 없으며, 검증기(validator)가 검사할 형상도 존재하지 않습니다.

규칙의 두 번째 절반은 동기화 (Sync) 통화를 손상되지 않게 유지해 줍니다. 윈도우는 패킹과 병합 사이에서만 존재합니다. 모든 윈도우에 판정이 내려지면 이들은 하나의 테이블로 다시 조립됩니다 — 첫 번째 윈도우 전체, 그리고 컨텍스트로만 전달되었던 헤더와 구분자 행이 제거된 이후 윈도우들 — 그리고 병합된 테이블은 수락되기 전에 원문 (Source) 블록 (Block)의 열 개수, 정렬 (Alignment), 본문 행 개수를 기준으로 다시 검사됩니다. 재생성 이후부터는 부모의 ID를 가진 하나의 블록 (Block)으로 다시 돌아갑니다.

따라서 위에서 설명한 ID 체인은 중요한 위치에서 유지되지만, 한 가지 솔직한 제한 사항이 있습니다: *와이어* 상에서, 그리고 검증 (Validation) 보고서 내에서 ID는 이제 윈도우 ID(부모 블록 (Block) ID에 윈도우 서수가 추가된 형태)가 될 수 있으며, 이는 정렬 (Alignment) 맵과 DOM 내에서 아무것도 가리키지 않습니다. 보고서의 모든 유닛 ID가 렌더링된 앵커로 해소된다고 가정했던 도구는 더 이상 유효하지 않은 사실에 의존하고 있었던 것입니다. 정렬 (Alignment) 맵과 `data-sync-id` 속성은 변경되지 않았습니다: 분할기가 존재하기 전과 정확히 동일하게 원문 (Source) 블록 (Block)당 하나의 행, 하나의 앵커가 유지됩니다.

## 당연한 귀결: JavaScript는 결코 Markdown을 파싱하지 않습니다

블록 (Block) ID가 유일한 동기화 (Sync) 통화가 되면 두 번째 디자인 (Design) 질문이 즉시 따릅니다: 누가 블록 (Block)이 무엇인지 *결정*하도록 허용되는가? 브라우저가 자체 DOM을 구축하기 위해 Markdown을 독립적으로 파싱한다면, 한 블록 (Block)이 끝나고 다음 블록 (Block)이 시작되는 위치에 대해 Rust (Rust) 파서와 의견이 달라질 수 있습니다 — 그리고 그러한 순간 전체 동기화 (Sync) 메커니즘이 의존하는 공유 ID 공간은 양쪽에서 동일한 의미를 갖지 않게 됩니다. 따라서 규칙은 무조건적입니다: JavaScript는 이미 렌더링되고 이미 ID 주석이 달린 (Annotated) 콘텐츠에 마운트되고 반응할 뿐, 자체 Markdown 파서를 결코 실행하지 않습니다. 오늘날 두 가지 경로가 이 규칙을 만족합니다 — CLI가 주석이 달린 (Annotated) HTML을 직접 배출하거나, (ADR-0019 이후) 동일한 Rust (Rust) 렌더러 (Renderer)가 WebAssembly로 컴파일되어 브라우저 *내에서* 실행되는 것입니다 — 그리고 규율에 의해 동기화 (Sync) 상태를 유지해야 하는 두 가지 구현체가 아니라 어느 쪽이든 동일한 렌더러 (Renderer)이기 때문에 두 경로 모두 바이트 단위로 동일한 조각(fragment)을 생성합니다.

동일성은 양방향으로 작용하며, 이는 기능입니다: 렌더러 (Renderer)가 슬라이스할 수 없는 바이트 범위를 가진 정렬 (Alignment) 행을 거부하도록 변경되었을 때, 두 경로 모두 동일한 편집에서 거부 특성을 상속받았습니다. 어느 한쪽이 문제를 보고하는 동안 다른 한쪽이 올바르게 보이는 앵커 아래에서 잘린 블록 (Block)을 무심코 표현하는 일은 일어날 수 없습니다.

## 제공자 경계가 들어맞는 위치

관련되면서 별도로 결정된 질문은 LLM에 대한 네트워크 호출을 누가 소유하는가입니다. ADR-0002는 코어 파이프라인을 HTTP-free 상태로 유지합니다: 구체적인 제공자가 아닌 `Translator` 트레이트에 의존합니다. 이는 동기화 (Sync) 통화와는 전혀 관련이 없는 별도로 내려진 이식성 및 테스트 가능성 결정이며, ID 우선 디자인 (Design)과 깔끔하게 합성됩니다: `TranslationUnit`이 이미 "하나의 블록 (Block), 하나의 ID, 하나의 페이로드"이기 때문에 트레이트를 구현하는 모든 제공자는 왜 그것이 중요한지 알 필요 없이 ID 보존 계약을 자동으로 상속받습니다.

DCR-0029 이후 이 주장은 주장이 아닌 실증이 되었습니다. 트리에는 동일한 트레이트를 진정으로 다른 HTTP 표면(다른 인증 헤더, 필수 프로토콜 버전 헤더, 생략을 수용하는 대신 모든 요청에서 API (API)가 요구하는 출력 상한)을 대상으로 구현하는 두 개의 제공자 크레이트 (Crate)(OpenAI 어댑터 및 Anthropic 어댑터)가 존재합니다. 이러한 부분 중 그 무엇도 코어에 도달하지 않았습니다. 두 번째 구현이 변경한 사항은 이식성 주장 자체보다 더 큰 가치가 있습니다: 공유 오류 어휘 목록에 하나의 용어를 추가했습니다. 지나치게 긴 *요청*과 잘린 *응답*은 둘 다 토큰에 관한 것이며, 둘 다 최종적이고, 서로 반대되는 노브를 가리키므로, 이를 병합했다면 도움이 되지 않는 구제책을 명시했을 것입니다 — 그 구분을 가장 먼저 마주한 어댑터 덕분에 이제 트레이트가 각각에 대한 이름을 갖게 되었습니다. 대략 올바른 위치에 그려진 경계가 실전에서 보여주는 모습이 바로 이것입니다: 두 번째 구현에 필요한 비용은 재디자인 (Design)이 아닌 어휘의 추가뿐이었습니다.

한 가지 솔직한 한계: 참조 CLI는 두 번째 제공자를 선택할 수 없습니다. CLI는 OpenAI 크레이트 (Crate)에만 의존하며 제공자 플래그가 없습니다. `--provider` 축은 실제 디자인 (Design) 작업(환경 표면, 키 해소, 인수 계약 변경)이기 때문이며 DCR-0029가 의도적으로 자체 범위에서 제외시켰습니다. 오늘날 Anthropic 어댑터에 도달하려면 [사용자 지정 번역기 (Translator) 제공자 구현 방법](../../../how-to/developer/ko/implement-a-custom-translator.md)에서 직접 작성하는 제공자에 대해 설명하는 방식 그대로 라이브러리를 호출하고 자체 `Translator`를 파이프라인에 전달해야 합니다.
