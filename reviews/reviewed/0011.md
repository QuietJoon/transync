## High severity

**[HIGH] The live-smoke workdir assignment is syntactically fused**
**Issue ID:** R0011-0001
**Location:** scripts/smoke-live.sh:64
**Impact:** The ordinary live-smoke entry point reaches its first use of `WORKDIR` with that variable unset under `set -u`, so the documented paid-provider workflow is broken before translation starts.
**Evidence / reasoning:** `DEFAULT_WORKDIR="$(...)"WORKDIR="..."` is one assignment word, not two shell assignments; the characters intended to declare `WORKDIR` become part of `DEFAULT_WORKDIR`'s value.
**Recommendation:** Put the `DEFAULT_WORKDIR` and `WORKDIR` assignments on separate lines and add a static shell-syntax gate for these scripts.
**Ignore/Decision reference:** Not mentioned

**[HIGH] The long live-smoke wrapper fuses an assignment with `export`**
**Issue ID:** R0011-0002
**Location:** scripts/smoke-live-long.sh:36
**Impact:** The long-running live workflow exports neither the intended default nor a valid workdir value and then delegates to the already-broken base smoke script.
**Evidence / reasoning:** `DEFAULT_LONG_WORKDIR="$(...)"export TRANSYNC_LIVE_WORKDIR=...` is parsed as one assignment whose value contains the word `export`; no export command is executed.
**Recommendation:** Split the command substitution assignment from the export and keep the derived default in a separately quoted variable.
**Ignore/Decision reference:** Not mentioned

**[HIGH] Any marker contents grant out-dir ownership**
**Issue ID:** R0011-0003
**Location:** crates/transync-cli/src/output/preflight.rs:416
**Impact:** An accidental or corrupt regular file named like the ownership marker can authorize replacement of a sparse output directory that the tool did not create, risking unrelated data loss.
**Evidence / reasoning:** Ownership is set from the marker filename and file type alone. The canonical `OUT_DIR_MARKER_BODY` written by the publisher is never read or compared during preflight.
**Recommendation:** Require an exact, bounded marker-body match before treating the directory as owned; otherwise continue through the conservative complete-fileset check.
**Ignore/Decision reference:** DCR-0024 defines publication mechanics but does not authorize accepting arbitrary marker contents.

**[HIGH] Disk-cache compaction cannot replace an existing log on Windows**
**Issue ID:** R0011-0004
**Location:** crates/transync-core/src/cache/disk.rs:808
**Impact:** Every normal compaction of an existing cache log fails on Windows, so the append-only file can keep growing while the advertised byte ceiling is not restored.
**Evidence / reasoning:** `std::fs::rename(temp_path, path)` replaces an existing file on Unix but fails when the destination exists on Windows; the live cache log necessarily exists at compaction time.
**Recommendation:** Implement a platform-safe replace protocol with a same-directory backup and rollback, or use an already-reviewed atomic-replace abstraction.
**Ignore/Decision reference:** Not mentioned

**[HIGH] Compaction temp creation can truncate an existing temp file**
**Issue ID:** R0011-0005
**Location:** crates/transync-core/src/cache/disk.rs:740
**Impact:** A name collision can destroy evidence from another interrupted compaction and let two writers interfere with the same staging file before the final rename.
**Evidence / reasoning:** The temp name is time/PID based, but `File::create` truncates if it already exists. The same process can reuse the name when the clock source collapses or concurrent attempts share the timestamp.
**Recommendation:** Open with `create_new(true)` and retry with a collision-resistant nonce; never adopt or truncate a pre-existing compaction temp.
**Ignore/Decision reference:** DCR-0026 permits same-process concurrency but does not make truncating temp adoption safe.

**[HIGH] Accepted asynchronous Responses jobs are resubmitted instead of polled**
**Issue ID:** R0011-0006
**Location:** crates/transync-provider-openai/src/responses.rs:259
**Impact:** A `queued` or `in_progress` response can cause a second paid request for the same batch, duplicating work and potentially cost while abandoning the accepted job identifier.
**Evidence / reasoning:** Both statuses become `ProviderError::Transient`; the shared retry loop repeats the original POST rather than polling the returned response resource.
**Recommendation:** Poll the accepted response by ID, or classify these states as a distinct pending outcome that cannot enter request-resubmission retries.
**Ignore/Decision reference:** DCR-0012 bounds retries but does not define asynchronous-job handling.
