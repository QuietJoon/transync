# 계층화된 검증 및 제한된 재시도/폴백인 이유

`Translator` 구현체는 구조화된 JSON을 요청받으며, Structured-Outputs 기능이 있는 모델에서는 보통 요청받은 정확한 형상을 반환합니다. 검증을 거기서 멈추고 싶은 유혹이 들 수 있습니다. transync는 그렇지 않으며, 그 이유들은 계층별로 따지는 대신 전체로서 이해할 가치가 있는 형상으로 구성됩니다.

## 스키마 준수가 내용의 정당성을 의미하지는 않음

모델은 완전히 유효한 JSON — 올바른 키, 올바른 타입 — 을 반환하면서도 JSON Schema에 표현되지 않는 한 가지를 은밀하게 위반할 수 있습니다: 마크다운 테이블이 여전히 동일한 열 개수를 유지하는지, 코드 펜스의 언어 태그가 유지되었는지, 링크의 대상이 주변 본문과 함께 의역되지 않았는지 등입니다. 이 중 어느 것도 스키마 위반이 아닙니다. 이는 *구조적* 위반이며, 구조적 무결성은 모델이 아닌 애플리케이션이 소유해야 하는 부분입니다(불변식 2: LLM은 내용을 소유하고 애플리케이션은 구조를 소유함). 따라서 JSON Schema가 표현할 수 없는 페이로드 바이트 규칙이 존재하고 배치 엔벨로프 오류가 귀속되는 스키마 계층 다음으로, 파이프라인은 ID 세트(누락 없음, 추가 없음, 중복 없음), 블록 종류별 형상(테이블 열, 리스트 깊이, 인용구 자식, 코드 펜스 메타데이터, 헤딩 레벨, 원시 HTML 세그먼트 수)을 검사한 다음, 번역된 프래그먼트를 GFM 하에서 다시 파싱하여 여전히 동일한 *종류*의 블록인지 확인하고, 인라인 보호(링크 및 이미지 대상, 원시 인라인 HTML 태그 동일성, 정책이 요구하는 경우 코드 스팬 동일성)를 검사합니다. 각 계층은 이전 계층이 감지할 수 없는 실패 모드를 포착합니다.

최종 계층은 나머지 계층들과 성격이 다릅니다: 모든 유닛이 개별적으로 유효한 후, 재생성된 전체 문서가 다시 파싱되고 앵커 개수와 순서가 원문과 비교하여 검사됩니다. 이는 계층 접합부에만 존재하는 드리프트 — 즉, 개별 유닛 검사만으로는 감지할 수 없는, 문서 문법을 다르게 만드는 연결(splice) — 를 포착합니다. 유닛 유효성이 명시적으로 2단계(*프로비저널(provisional)* 개별 유닛 단위, 전체 문서 재파싱 후에만 *파이널(final)*)로 관리되는 이유가 여기에 있습니다: 유닛은 모든 개별 유닛 게이트를 통과하더라도, 포함된 문서가 하나로 유지되지 않으면 나중에 강등될 수 있습니다.

## 계층화는 안전망이 아니며, 양날의 검임

6개 계층 스택에 대한 편안한 해석은 한 계층의 구멍이 다음 계층에서 포착된다는 것입니다. 이러한 해석은 틀렸으며, 이 프로젝트에는 이론적인 우려가 아닌 구체적인 반례가 존재합니다.

원시 HTML 계층은 원래 *비어 있는* 번역 세그먼트를 거부했습니다. 공백 하나로 이루어진 세그먼트는 비어 있지 않습니다. 이는 마크업 보존 공백으로 다시 연결(splice)되므로 연결에 성공하고, 태그 인벤토리가 일치하며, 프래그먼트 재파싱이 일치하고, 전체 문서 재파싱도 일치합니다 — 이후의 모든 계층이 동의하는데, *구조적*으로 변경된 것이 없기 때문입니다. 그 결과 보이는 문장이 사라진 채 블록이 `translated` 상태로 표시되어 전달되었습니다. 구조를 검사하는 두 번째 계층 이후의 그 어떤 계층도 이를 감지할 수 없었습니다. 해결책(ADR-0018을 수정하는 DCR-0025)은 추출기가 이미 적용하고 있던 규칙을 가장 초기 계층에서 명시하는 것이었습니다: 세그먼트 스캐너는 *디코딩된* 형태가 공백 이외의 다른 것을 포함하는 경우에만 원문 텍스트 노드를 유지하므로, 공백 전용 원문 세그먼트는 존재할 수 없으며 공백 전용 응답은 정당한 의미를 가질 수 없습니다. 따라서 이를 거부하는 것은 오탐(false positive)이 없으며, 거부는 해당 계층의 나머지 부분과 마찬가지로 재시도 가능합니다 — 거부 메시지는 올바른 공급자 응답(원문 세그먼트를 다시 에코하는 것)까지 밝힙니다.

동일한 패스에서 닫힌 코드 펜스 규칙도 동일한 형상을 갖습니다. 펜스 메타데이터는 *원문* 펜스에 정보 문자열(info string)이 포함된 경우에만 비교되었으므로, 정보가 없는 펜스의 번역 결과가 Rust 태그가 지정된 펜스로 돌아와도 그대로 통과되었습니다 — 그리고 재생성은 *번역된* 페이로드에서 정보 문자열을 읽어오므로 지어낸 언어 태그가 출력 파일에 도달했습니다. 이는 `None → Some` 방향이며, 어떤 결정도 이를 허용한 적이 없습니다: 코드 블록의 언어를 선택하는 것은 구조적 결정이며, 불변식 2에 따라 애플리케이션 전용입니다. 이미 올바르고 변경되지 않은 `Some → Some` 축어적 규칙 대신, 부재한 정보 문자열을 조기 반환하는 대신 규칙으로 명시하도록 변경되었습니다.

대칭적인 위험은 잊어버리기 쉽고 출력에 동일한 고통을 줍니다. 오류를 *지어내는* 검증은 오류를 놓치는 검증만큼이나 확실하게 문서를 손상시킵니다. 원시 HTML 토크나이저는 이전에 `Rows <2026 total> here`와 같은 일반적인 본문이 마크업으로 등록되도록 숫자로 시작하는 태그 이름을 허용했습니다. 엔진은 연결된 결과의 태그 인벤토리를 원문의 태그 인벤토리와 비교하여 번역된 HTML 블록이 마크업을 보존했음을 증명합니다; 유령 항목으로 인해 해당 비교가 불일치하게 되었고 완전히 정상적인 번역이 원문 내용으로 강등되었으며, 재구축 경로에서 동일한 오스캔으로 인해 작성된 `</1>`이 창에서 완전히 삭제될 수 있었습니다. 그 비교는 아래에 설명된 엔진 오류 경로 중 하나이기 때문에 강등 조치 또한 즉각적이었습니다 — 계층 이름이 지정되지 않았고 재시도도 시도되지 않았습니다. 가드가 엄격하다고 해서 무조건 안전한 쪽에 서게 되는 것은 아닙니다.

## 가드(guard)가 거부할 수 있는 위치

"조용히 성능 저하(degrade)시키지 말고 거부(refuse)하라"는 이 페이지의 주된 지침이며, 이 지침이 무조건적인 것은 아니라는 점을 솔직히 밝힐 필요가 있습니다. 코드베이스에는 의도적으로 서로 다른 세 가지 방식으로 답변된 동일한 질문이 포함되어 있으며, 매번 결정적인 요인은 접합부(seam)가 오류 채널을 소유하고 있는지 여부입니다.

렌더러는 거부합니다. 뒤집히거나, 창의 마크다운 끝을 지나치거나, UTF-8 문자 내부에 위치하는 바이트 범위는 해당 창의 슬라이스가 아니며, DCR-0025 이후 창은 해당 블록 ID와 오프셋 및 사유를 명시하면서 렌더링을 완전히 거부합니다. 이전에는 이러한 범위를 살아남은 바이트로 고정하고 잘라냈는데(clamp and snap), 이는 여전히 렌더링되므로 정렬 행이 잘못된 바이트를 가리키는 블록이 올바르게 보이는 앵커 아래에 잘리거나 비어 있거나 관련 없는 콘텐츠로 표시되었습니다. 헷갈리기 쉽기 때문에 두 가지 세부사항을 정확히 명시할 필요가 있습니다: 여기서 새로운 오류 발생 가능한(fallible) 호출이 추가된 것은 아닙니다. 중복되거나 누락된 정렬 행이 거부되기 시작하면서 렌더러 생성은 더 일찍 오류 발생 가능하게 되었습니다(DCR-0022); DCR-0025가 추가한 것은 기존의 의도적인 비엄격 오류 타입에 새로운 *거부 사유*를 추가한 것입니다. 그리고 CLI 번들과 WebAssembly 데모는 동일한 렌더러이므로 둘 중 하나가 이전의 강제 조치를 유지하는 대신 모두 거부를 상속받습니다.

재생성(Regeneration)은 거부하지 않습니다. 구조상 오류가 발생하지 않습니다(infallible) — 호출자가 오류를 전달할 곳이 없기 때문입니다 — 따라서 재생성에 있어 clamp-and-snap은 *안전한* 답이며 대안은 패닉입니다. snapping을 수행하는 공유 헬퍼는 이러한 이유로 정확히 하나의 호출자만 가지며, 자체 문서에 해당 분리를 기록하고 있습니다.

정렬 맵 생성은 경고합니다. 불완전한 오프셋이 전달되면 처리되지 않은 블록에 대해 여전히 빈 범위를 내보내는데, 빈 범위가 거기서 진정으로 안전한 값이기 때문이며, 배포된 어떤 경로도 생성할 수 없는 입력에 대해 모든 호출자가 `Result`를 처리하도록 강제하는 대신 `tracing` 경고로 해당 블록 이름을 명시합니다. 이는 실제 명시된 한계입니다: `tracing` 구독자를 설치하지 않은 임베더는 아무것도 볼 수 없습니다.

재사용 가능한 규칙은 "항상 거부하라"가 아닙니다. 규칙은 다음과 같습니다: 거부할 수 있는 접합부는 거부해야 하며, 거부할 수 없는 접합부는 콘텐츠처럼 보이는 값 대신 다른 곳에서 요란하게 실패하는 값을 선택해야 합니다.

## 재시도: 제한되고 축어적이며 의도적으로 스마트하지 않음

언제 유닛이 검증에 실패할 때 명백한 다음 단계는 "모델에 무엇이 잘못되었는지 알리고 다시 요청하는 것"처럼 보입니다. transync의 재시도는 더 좁은 작업을 수행합니다: *정확히 동일한 요청*(동일한 페이로드, 동일한 범위)을 다시 제출하고, 무제한 코칭 루프 대신 제한된 예산(기본값: 2회 재시도, 즉 총 3회의 콘텐츠 시도)으로 준수 형상을 생성하기 위해 모델 자체의 확률적 변동성에 의존합니다.

이것은 쉽게 놓치기 쉬운 이유로 두 번에 걸쳐 독립적으로 검토되고 이의가 제기되었으며(ADR-0009) 두 번 모두 유지되었습니다: **분명히 더 나아 보이는 수정 방식이 안전하지 않다는 것입니다.** 모델이 보는 페이로드에 교정 지침을 넣는 방식이 시도되었습니다. 잘 작동하는 번역기가 해야 할 일을 정확히 수행하는 충실한 모델은 다른 모든 것과 함께 지침 텍스트를 번역하고 이를 추가 블록으로 다시 에코합니다 — 그러면 전체 문서 재파싱은 원래 있어야 할 블록보다 명백히 하나가 더 많기 때문에 이를 올바르게 거부합니다. 수정하려던 방식이 개선하려던 대상을 망가뜨렸습니다. 그 대신 필요에 따라 배포된 것은 페이로드 *옆*에 나란히 전달되는 비콘텐츠 사이드 채널(`RetryContext`: 시도 횟수, 이전 시도를 거부한 계층, 짧은 사유)입니다 — `source_payload` 내부가 아닌 시스템 프롬프트 프레이밍에 전달됨 — 따라서 모델은 힌트를 출력으로 유출하지 않고 사용할 수 있습니다. 축어적 재제출 규칙 자체는 변경된 적이 없으며, 선택적 지침을 위한 채널만 그 위에 추가되었습니다.

행 창 분할(Row-window splitting)은 해당 규칙의 흥미로운 스트레스 테스트이며, 규칙을 수정하지 않고 통과합니다. 너무 큰 테이블은 첫 번째 공급자 호출 전, 결정론적인 *패킹* 시점에 헤더를 포함하는 창으로 분할됩니다 — 이는 배치 경계를 결정하는 것과 동일한 종류의 작업입니다. 패킹 이후에는 어떤 것도 유닛의 범위를 다시 조정하지 않습니다: 반응형 재분할은 없으며, 실패나 공급자 신호가 창을 줄이지 않으며, 창은 태어날 때부터 전체 실행 동안 범위가 고정된 일반 유닛입니다. 따라서 검증에 실패한 창은 다른 유닛과 마찬가지로 축어적으로 다시 제출되어 자체 콘텐츠 예산에 차감됩니다. 문서화된 최악의 경우 라운드 바운드는 소스 테이블 대신 창을 세는 유닛 개수와 함께 여전히 유지됩니다.

동일한 보수주의는 재시도 예산이 차감되는 방식에서도 나타납니다. 한 유닛의 결과 행을 누락한 공급자와 형제 유닛을 잘못 번역한 공급자는 서로 다른 실패이며, DCR-0014 기준으로 서로 다른 예산에 차감됩니다 — *배치 엔벨로프* 오류(행 누락 또는 중복)는 별도의 라운드당 1회 예산을 소모하므로, 내용이 실제로 평가되지 않은 유닛이 단순히 틀린 유닛보다 실제 번역 시도 횟수가 적어지지 않습니다. 실패 모드 간의 공정성을 위해 공유 카운터가 아닌 별도의 회계가 필요함이 드러났습니다. 일시적인 전송 오류에 대한 세 번째 예산은 배치가 다른 디스패치 라운드에 진입할 때 의도적으로 리셋되지 *않습니다*: 전체 사다리에 걸쳐 적용되므로 배치는 검증에 실패함으로써 네트워크 시도 횟수를 다시 얻을 수 없습니다.

## 누구의 예산으로 지불하는가: 모델 오류, 공급자 오류, 엔진 오류

이 세 가지 범주 중 두 가지는 대부분의 디자인이 예상하는 범주입니다. 세 번째 범주는 보고서의 의미를 바꾸기 때문에 이름을 붙일 가치가 있는 범주입니다.

*엔진* 오류는 페이로드가 이미 수락된 후 발견된, 모델이 원인이 아닌 실패입니다. 오늘날에는 두 가지가 있습니다. 하나는 세그먼트가 잘 돌아왔으나 연결(splice)이 실패했거나 연결 결과에 더 이상 원문의 마크업이 포함되지 않는 원시 HTML 블록입니다. 다른 하나는 행 창 분할과 함께 도입되었습니다: 모든 창이 자체 계층을 통과한 후, 창들이 다시 하나의 테이블로 병합되고 병합된 테이블은 *원문* 블록의 열 개수, 열별 정렬 및 본문 행 개수에 대해 다시 검사됩니다. 해당 검사가 실패하면 모델 출력이 잘못된 것이 아니라 엔진 자체의 재조립이 잘못된 것입니다.

둘 다 동일한 형태를 취하며, 의도적으로 재시도가 아닙니다: 거부 계층 및 기록된 거부 사유가 없고, 재시도 예산이 소모되지 않으며, 병합 케이스의 경우 모든 창의 캐시 항목이 제거되어 원문 콘텐츠로 직접 폴백하므로, 공유 캐시에 대한 재실행이 동일한 고장 상태를 결정론적으로 다시 재생할 수 없습니다. 엔진의 실수에 모델의 예산을 쓰는 것은 정직하지 못한 회계가 될 것이며, 결과를 캐싱하면 일시적인 엔진 오류가 영구화될 것입니다.

실행을 감사하는 모든 사람에게 주는 시사점은 구체적입니다: `rejected_by` 단독으로는 모든 `fallback_source`를 설명하지 못합니다. 그 중 두 개는 거부 계층이 없으며 원인이 기록되는 유일한 장소는 보고서의 경고 채널입니다.

## 폴백은 기록(paper trail)이 남는 최종 수단임 — 한 가지 구멍을 제외하고

유닛의 재시도가 소진되면 대상 문서에서 번역되지 않은 원문 콘텐츠로 폴백하며, 정렬 맵에 `fallback_status`로 명시적으로 표시됩니다. 이곳은 파이프라인이 실제 번역 이외의 것을 전달하도록 허용되는 유일한 장소이며, 유연하게 넘어가는 대신 의도적으로 시각화됩니다: 모든 블록의 최종 상태는 맵에 있으며, 검증 보고서는 실패한 각 시도를 거부한 계층의 이름을 명시합니다.

행 창 분할은 해당 보장을 약화시켰으며, 그 약화는 주장을 빼는 대신 솔직하게 명시할 가치가 있습니다. 분할된 테이블은 `partially_translated`로 최종 확정될 수 있습니다: 성공한 창은 번역된 행을 기여하고 터미널 실패한 창은 자체 *원문* 행을 기여하므로 한 테이블이 각 언어로 반씩 전달될 수 있습니다. 정렬 맵은 해당 블록에 `partially_translated`를 기록하지만 — 오직 해당 블록에만 기록합니다. **어느** 행이 폴백되었는지는 맵과 DOM에 존재하지 않는데, 창 ID가 둘 다에 도달하지 않기 때문입니다; 창 ID는 와이어(wire)와 `validation-report.json`에만 존재하며, 유닛 ID가 부모 블록 ID에 창 서수를 더한 형태인 행으로 존재합니다. 실패한 창의 이름은 보고서의 경고 채널에만 명시되며, 렌더링된 출력에서 번역된 테이블 내부의 원어 행은 모델이 보존하기로 선택한 행과 정확히 똑같이 보입니다.

따라서 보장의 정직한 형태는 "모든 폴백은 정렬 맵에서 찾을 수 있다"보다 좁습니다. 그것은 다음과 같습니다: 모든 *블록*의 상태는 정렬 맵에 있으며, 그 사유 — 및 하위 블록 세부사항 — 는 검증 보고서에 있습니다. 맵만 감사하는 도구는 테이블이 부분적이라는 것만 확인하며, 어느 부분인지 확인하지 못합니다. 보고서를 읽는 소비자는 보고서 내부의 모든 유닛 ID가 블록의 이름을 지정한다고 가정하는 것도 멈춰야 합니다: 보고서의 스키마 마이너 버전 상향 이후, 그 중 일부는 어디에도 존재하지 않는 행 창의 이름을 지칭합니다.

## 배치 터미널 공급자 실패가 전체 실행을 중단하는 이유

폴백은 *검증* 실패 — 모델이 시도했지만 반환된 결과가 버티지 못함 — 를 위해 존재합니다. 잘린 출력, 거부, 전송 재시도 소진 등 *공급자* 수준의 실패를 위해 존재하지 않습니다. 배치에 그러한 일이 발생하면 작성된 출력 없이 전체 실행이 중단되며, 이는 자체로 합리적으로 들리는 두 가지 제안에 대해 의도적으로 재검토되고 유지되었습니다(ADR-0017): 해당 배치만 원문 콘텐츠로 강등하고 계속 진행하거나, 중단 대 강등을 호출자가 선택하는 정책 플래그로 만드는 것입니다.

둘 다 동일한 근본적인 이유로 거부되었습니다. CLI는 소비자가 반쯤 작성된 결과를 추론할 필요가 없도록 모든 출력 파일을 하나의 원자적 올오어나싱(all-or-nothing) 스테이징 세트로 이미 커밋합니다(DCR-0006 / DCR-0011). 배치별 폴백 단계는 스테이징이 제거하기 위해 존재하는 바로 그 모호함을 은밀하게 다시 도입할 것입니다: 중간 어딘가에 번역되지 않은 섬을 조용히 포함한 채 `0`(성공)으로 종료되는 실행은 원시 마크다운에서 *원래* 원어로 유지되기로 되어 있던 단락과 구별할 수 없습니다. 진단과 함께 요란하게 중단되는 것은 발생하는 즉시 실패가 눈에 보이기 때문에 자체 교정적입니다; 숨겨진 갭이 있는 문서는 바이링구얼 독자가 해당 단락에 도달할 때까지 아무것도 잘못되어 보이지 않기 때문에 그렇지 않습니다. 정책 플래그 옵션은 관련된 근거로 거부되었습니다: "때로는 중단하고 때로는 조용히 강등함"은 출력의 모든 소비자가 처리해야 하는 상태를 두 배로 늘리며, 유일한 정직한 용도가 "혼합 언어 문서를 출하할 의향이 있음"인 모드를 제공할 뿐입니다 — 이 형태는 디자인이 최우선으로 지원하려는 형상이 아닙니다.

이것이 수용하는 트레이드오프는 실제적이고 명시적이며, 행 창 분할기가 출시된 이후 이전보다 좁아졌습니다. 요청이 전달할 수 있는 출력 제한 아래에 단일 블록의 번역이 도저히 들어갈 수 없는 **경계 문서(boundary document)**는 작업자가 제한을 높이거나 소스를 수동으로 분할할 때까지 번역할 수 없었습니다. 테이블의 경우 이것이 끝났습니다: 크기가 초과된 테이블은 이제 패킹 시점에 헤더를 포함하는 행 창으로 분할되고 나중에 재조립됩니다. 하지만 분할기가 *어디*에 위치하는지 주목하세요. 그것은 single request가 나가기 전에 예산을 초과한 유닛을 경고하고 이름을 지정하는 사전 확인 및 출력 인식 패킹과 함께 ADR-0017의 예방 쪽에 있습니다; 런타임에 공급자 실패를 포착하는 폴백 단계가 아닙니다. 패킹 *이후* 공급자 측의 크기 초과 신호는 ADR-0017이 결정한 대로 여전히 터미널 상태이며, 자체 창에조차 들어갈 수 없을 정도로 큰 단일 테이블 행은 여전히 실행을 중단합니다.

다른 모든 블록 종류는 ADR-0017의 시맨틱을 변경 없이 유지합니다 — 단락, 코드 블록(불변식 4는 펜스를 불가분으로 만듦), 리스트 항목, 인용구, 원시 HTML — 각각 누락이 아닌 기록된 종류별 결정에 의해 분할에서 제외됩니다. 그리고 분할기가 귀하의 실행에 대해 활성화되어 있는지 여부는 엔진의 속성이 아니라 프로필 문제입니다: 내장된 기본 프로필은 이를 켜지만, 키를 생략한 수동 작성 프로필은 조용히 전체 블록으로 해석되며, 이는 귀하가 선택했다는 경고가 없는 분할기 이전 동작입니다. [프로필 스키마 참조](../../../reference/user/en/profile-toml-schema.md)는 작업자가 필요로 하는 형식으로 해당 트랩을 문서화합니다.
